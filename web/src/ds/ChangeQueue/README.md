# ChangeQueue

A run's tests in the order a person works through them. Given `renderDetail`, it is the whole triage view: the queue beside the selected test.

- **Groups, in this order:** *New failures*, *Still failing*, *Fixed*, *New tests*, then *Removed tests*, closed until opened, or for an interrupted or abandoned run *Not reached*. Within a group, collection order; never re-sort.
- **Rows:** the outcome mark, the node id truncated so the function and its parameters survive, the duration, and one line of change in the detail's own words: *passed in 1adf29af*, *failing 4 runs since 1ad93e49*, *not in 1adf29af*.
- The first row of the first group is selected until something else is. Under the groups, always in view, *All 214 results* opens the whole run in collection order, with outcome filters; the keys are named under that.
- **Keys.** Each group is a list box named by its heading, and one selection runs across them. The arrow keys or `j` and `k` move, Home and End jump, Enter opens the result page (in one pane, it shows the test), and `c` copies the selected test's rerun command. With `shortcuts`, `j`, `k` and `c` work anywhere on the page and `/` focuses the filter; no key fires inside a text field, a menu or a dialog. The foot names the keys, and says what was copied.
- **Sizes.** Groups show 50 rows, then *Show 2,950 more*. The whole-run view pages by 200 and says how many are not shown; its outcome filter wraps onto a second line rather than hide an outcome and its count. The filter matches node ids whatever their case, and each heading then counts *2 of 8*.
- **Paged by the server.** A run can hold tens of thousands of results, so the queue can be fed a page at a time. Pass `totals`, how many tests each group holds (the six changes, and `failures` for a run with nothing to compare with), and the rows loaded so far as `results`. A group shows when its total is not zero, loaded or not, and its head prints the total. *Show 200 more* calls `onMore(group)` when it wants rows past those loaded, and so does opening a group with none loaded, such as *Removed tests*; `loading` names the groups waiting, whose button is busy (*Loading* and the block cursor) while the rows already shown stay. The whole-run view is fed the same way: `allResults`, the run's `outcomeCounts` for its filter, and `outcome` with `onOutcome`, since the server filters; opening it with nothing loaded calls `onMore('all')`. Fed whole, without `totals`, the queue behaves as it always has.
- **The filter searches only what has loaded, and says so.** A group not wholly loaded counts *2 of 50 loaded · 180 in all* and offers *Load 130 more* beside *130 not loaded, so not searched*; with no match anywhere, *No loaded test here matches `uart`; 310 not loaded were not searched.* It never implies it searched rows it has not seen.
- **Two panes from 900px of its own width**, a window about 950px wide. The queue takes 38% and fits the viewport below where it starts, so its foot is in view from the first load; as the page scrolls it grows until it sticks at the top, and it scrolls on its own. The detail flows beside it. Narrower, one pane at a time, and the queue flows with the page, so nothing in it is clipped: choosing a test shows its detail, with *Changed tests (2 of 8)* to go back and previous and next buttons. Focus moves into the detail, and back to the row.
- **States.** Nothing changed: *Nothing changed since 1adf29af.*, then any tests still failing, or *No failures.* No baseline: `baselineNote` (*Nothing to compare with yet.*), then the failures. Running: a run is compared once it ends, so the queue lists failures as they arrive, and its `baselineNote` says so (*The failures so far. Changes show once the session ends.*); the selection holds, and a polite live region says *2 failures so far*.
- Keep the selected node id in the page's address through `onSelect`, so a shared link opens on that test.
- Consumer provides: `results` in collection order (`nodeid`, `outcome`, `seconds`, `change`, `was`, `streak`), `missing` (the baseline's tests this run lacks, with `was`), `interrupted`, `baseline` (`{ label }`, or null), `baselineNote`, `total`, `selected` and `onSelect`, `onOpen`, `commandFor`, `renderDetail(result, { command, baseline, index, count })`, `running`, `shortcuts`; paged, also `totals`, `onMore`, `loading`, `allResults`, `outcomeCounts`, `outcome` and `onOutcome`, with removed and not-reached tests among the `results` (outcome `null`) rather than in `missing`.

**Served.** The server compares each run with its baseline once, when the run gets its exit status, and serves the comparison with the run, each result's change, and the changed tests paged in queue order.

## Port notes

- Ported one to one, paging included: markup, `dl-` classes, words, aria and behaviour. `window.Dotline` and `createElement` become a typed TSX export, checked against `contract.d.ts` by `contract.test-d.ts`.
- A row's `chips` draw nothing. `RecordChip` belongs to recorded data and views, which the server does not serve yet and which are not ported; the prop stays in the type, as the contract has it, so the rows can carry chips once they are.
- A key that moves focus to a row moves it even when that row is already the selected one, as the down arrow from the filter does when the selected test still matches. The system asks for focus only through the render a new selection causes, so there, with the selection unchanged, React skips the render and focus stays in the filter; the port asks for a render of its own.
- Enter with no row selected, as when `selected` names a test that has not loaded, calls no `onOpen`, whose contract type takes a row; the system would pass `null`.
- A selection loaded past the rows its group shows, or in a closed group, is brought into view once for each selection: the group opens, shows rows down to it a step at a time as *Show more* would, and the row scrolls into view. In the system the row stays out of the list, nothing is selected and `j` starts again at the top, so an address naming a test past a group's first 50, or a removed one, as the run page writes them, would not open on it. It is for the system to take up, as the paging was; until then it stays a deviation.
- The detail's accessible name writes a node id's hidden characters as `⟨U+202E⟩` (`visibleText`), as every other plain string of recorded text does; the system names it with the node id as it is.
- `CHANGE_ORDER` and `changeNote` live in `lib/changes.ts`, beside the changes' words, as in the system's bundle; `isEditable` and `Kbd` stay in the module. Rows are looked up by node id in a `Map` rather than the system's plain object, so no node id can name an inherited property. `ChangeGlyph` comes from ChangeBadge and `rerunCommand` from RerunButton, so `c` copies a command guarded as RerunButton's port notes say: no node id read as an option or a file of arguments, and no control or hidden character in it.
